# LearnExa — AI-Powered RAG Learning Assistant

LearnExa lets you upload study documents (PDF or TXT) and ask questions about
them. Answers are generated by Google Gemini from the passages of your own
documents, and every answer shows the sources it was based on.

This is a portfolio project, built to be understood and explained end to end.
It is a working local application, not a production system (see
[Limitations](#limitations)).

## 1. What is LearnExa?

A full-stack Retrieval-Augmented Generation (RAG) application:

- **Frontend:** Next.js (App Router), React, TypeScript, Tailwind CSS
- **Backend:** Python, FastAPI, Pydantic
- **Vector database:** Chroma (stored locally)
- **AI:** Google Gemini for embeddings and for answer generation

## 2. Problem statement

Large language models do not know what is inside your lecture notes, and when
they are unsure they may produce confident but wrong answers. LearnExa
retrieves the relevant passages from your documents first, gives them to the
model as context, and shows you the sources, so you can check where an answer
came from. RAG reduces the risk of made-up answers but cannot guarantee that
every answer is correct.

## 3. Features

- Upload PDF and TXT files (drag and drop or file picker), up to 10 MB
- Per-page text extraction, so sources point to page numbers
- Ask questions about all documents or about one selected document
- Answers rendered as Markdown, with source cards (document, page, similarity
  score, expandable text)
- Documents page (list, delete) and a dashboard with simple statistics
- Friendly error messages for invalid files, Gemini problems and an offline
  backend
- Automatic retries when Gemini is temporarily busy or rate limited
- Light and dark mode (follows the operating system setting)
- 141 automated backend tests (pytest)

## 4. Architecture

```
Browser
  ↓
Next.js frontend (localhost:3000)
  ↓  HTTP REST (JSON / multipart), only through frontend/lib/api.ts
FastAPI backend (localhost:8000)
  ↓
RAG pipeline  ──→  Chroma (backend/data/chroma)
  ↓
Google Gemini (embeddings + answers)
```

The Gemini API key lives only in `backend/.env`. The browser never talks to
Gemini and never sees the key.

## 5. RAG pipeline

**Upload (ingestion)**

```
File → validate (type, empty, size) → extract text per page
     → split into overlapping chunks → embed each chunk (Gemini)
     → store text + vector + metadata in Chroma → record the document
```

**Question answering**

```
Question → embed the question (Gemini) → similarity search in Chroma
         → top-k chunks → build prompt (instructions + labelled sources + question)
         → Gemini generates the answer → return answer + sources
```

Key points of this implementation:

- **Chunking:** recursive splitting per page (LangChain's
  `RecursiveCharacterTextSplitter`), default 1000 characters with 150
  overlap. Splitting per page keeps page citations exact.
- **Embeddings:** Gemini embedding model (configurable). Chunks are embedded
  with the document task type and questions with the query task type.
- **Vector search:** a Chroma collection using cosine distance; each chunk
  stores `document_id`, `document_name`, `page_number` and `chunk_index`.
  Default top-k is 5.
- **Prompt:** lives in `backend/app/rag/prompts.py`. It tells the model to use
  only the supplied context, to say clearly when the answer is not there, and
  to cite source numbers.
- **No documents stored:** the backend answers with a fixed message and does
  not call Gemini at all.

## 8. Installation

You need Python 3.11 or newer, a recent Node.js (20 or newer), and a Gemini
API key from Google AI Studio.

## 9. Environment variables

Backend (`backend/.env`, created from `backend/.env.example`):

| Variable | Meaning | Default |
|---|---|---|
| `GEMINI_API_KEY` | Your Gemini API key (required) | empty |
| `GEMINI_MODEL` | Gemini model used for answers (required). Pick a current model name from Google's Gemini model list | empty |
| `GEMINI_EMBEDDING_MODEL` | Embedding model | `gemini-embedding-001` |
| `FRONTEND_ORIGIN` | Allowed browser origin (CORS) | `http://localhost:3000` |
| `CHUNK_SIZE` | Characters per chunk | `1000` |
| `CHUNK_OVERLAP` | Characters shared by neighbouring chunks | `150` |
| `TOP_K` | Chunks retrieved per question | `5` |
| `ENVIRONMENT` | Label shown by `/health` | `development` |

Frontend (optional): `NEXT_PUBLIC_API_URL` — backend address, default
`http://127.0.0.1:8000`.

Never commit `.env`. It is listed in `.gitignore`.

## 10. Backend setup (Windows, cmd)

```
cd backend
python -m venv .venv
.venv\Scripts\activate.bat
pip install -r requirements.txt
copy .env.example .env
```

Open `backend\.env` and set `GEMINI_API_KEY` and `GEMINI_MODEL`.

## 11. Frontend setup

```
cd frontend
npm install
```

## 12. Running the project

Terminal 1 (backend):

```
cd backend
.venv\Scripts\activate.bat
uvicorn app.main:app --reload
```

Terminal 2 (frontend):

```
cd frontend
npm run dev
```

Open http://localhost:3000. API documentation (Swagger) is at
http://localhost:8000/docs.

Run the backend tests (they never call Gemini):

```
cd backend
.venv\Scripts\activate.bat
pytest -v
```

API endpoints:

| Method | Path | Purpose |
|---|---|---|
| GET | `/health` | Status; reports only whether a key is configured |
| POST | `/api/documents/upload` | Upload and ingest a PDF or TXT file |
| GET | `/api/documents` | List uploaded documents |
| DELETE | `/api/documents/{document_id}` | Delete a document and its chunks |
| POST | `/api/chat` | Ask a question; returns answer and sources |

## 13. Example workflow

1. Open the Documents page and upload `Machine_Learning_Notes.pdf`.
2. Wait for the green confirmation (pages and chunks are shown). Large files
   take longer because of Gemini free-tier embedding limits.
3. Open Chat, choose the document, and ask "What is overfitting?".
4. Read the answer, then expand the source cards to see the passages and page
   numbers it was based on.

## 15. Future improvements

Ideas, not promises. None of these are implemented:

- Measure retrieval quality and decide whether a similarity cutoff, reranking
  or hybrid search is worthwhile
- Conversation memory across questions
- Background ingestion with progress instead of one long upload request
- Support for DOCX and PPTX
- User accounts and per-user document collections
- A real database instead of the JSON document list
- Automated frontend tests

## Limitations

- Built for a single local user. The document list is a JSON file with no
  locking, and there is no authentication.
- Scanned PDFs (images without text) are rejected; there is no OCR.
- Retrieval always returns the nearest chunks, even for an off-topic
  question. Only the prompt asks the model to say "not found". No similarity
  cutoff has been measured or added.
- Gemini free-tier limits and temporary overloads can slow or interrupt
  uploads and answers; the app retries temporary errors and then shows a
  friendly message.
- Answers can still be wrong. Always check the sources.
- Not production-ready.
